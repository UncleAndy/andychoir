# Mesh-сеть для AndyChoir: Децентрализованное обнаружение, маршрутизация и дедупликация

## 1. Обзор

AndyChoir поддерживает децентрализованную mesh-сеть хостов. Каждый хост может подключаться к одному или нескольким соседям, формируя граф. Цель — обеспечить доставку событий любому целевому хосту в сети без необходимости в центральном сервере (корне) или сложной ручной настройке.

Система достигает этого за счёт комбинации **Link-State обнаружения**, **локальной маршрутизации по кратчайшему пути** и **вероятностной дедупликации**.

**Транспорт.** По умолчанию хосты общаются по простому `ws://` (tokio-tungstenite поверх TCP). Чтобы зашифровать межхозяйский трафик и взаимно аутентифицировать узлы, включите **mTLS** с внутренним приватным CA — см. §8.6. mTLS опционален и выключен по умолчанию (обратная совместимость).

## 2. Децентрализованное обнаружение (Link-State)

Вместо центрального координатора каждый хост независимо поддерживает **LSDB (Link-State Database)** — локальную карту всей топологии сети.

### Протокол HELLO
- **Пакеты HELLO:** Каждый хост периодически рассылает сообщение `HELLO` своим прямым соседям.
- **Полезная нагрузка:** Сообщение `HELLO` содержит:
  - `source_id`: UUID отправляющего хоста (должен быть UUID v4/v7, не читаемая строка — см. §5).
  - `neighbors`: Список хостов, к которым этот узел подключён в данный момент.
  - `capabilities`: Набор инструментов/плагинов, доступных на этом хосте.
- **Распространение:** Когда хост получает `HELLO` от соседа, он обновляет свою локальную LSDB и пересылает сообщение другим соседям (если информация новая или обновилась).

### Поддержка LSDB
- **Сходимость:** Через несколько раундов каждый хост получает полную карту сети: `Узел А -> [B, C], Узел B -> [A, D], ...`.
- **Обнаружение сбоев:** Если от соседа нет сообщений в течение $N$ секунд, он помечается как офлайн, и LSDB обновляется.
- **Корректный выход:** Сообщение `BYE` уведомляет соседей о необходимости немедленно удалить хост из базы.

## 3. Маршрутизация: локальный кратчайший путь

Так как каждый хост владеет полной картой сети (LSDB), он может вычислить оптимальный маршрут к любой цели без центрального корня.

### Расчёт маршрута
- **Кратчайший путь:** При получении события для удалённого `target_id` хост запускает алгоритм поиска кратчайшего пути (например, алгоритм Дейкстры) по своей локальной LSDB.
- **Следующий прыжок (Next Hop):** Хост определяет ближайшего соседа, который лежит на кратчайшем пути к цели, и пересылает событие только этому соседу.
- **Избегание петель:** Маршрутизация по кратчайшему пути на статическом снимке LSDB по определению не создаёт циклов. Если топология меняется в момент передачи, механизм **TTL** служит страховкой.

### Таблица маршрутизации
Чтобы не пересчитывать путь для каждого пакета, каждый хост поддерживает локальную **таблицу маршрутизации** (FIB):
`target_id` $\rightarrow$ `next_hop_neighbor`.

## 4. Дедупликация и защита от петель

Чтобы события обрабатывались ровно один раз и не циркулировали бесконечно, система использует комбинацию вероятностной дедупликации и TTL.

### Bloom Filter (фильтр Блума)
Чтобы не хранить каждый `event_id` (что раздуло бы память), каждый хост использует **фильтр Блума**:
- **Фиксированный размер:** Выделяется небольшой битовый массив (например, 4 КБ).
- **Проверка:** Когда приходит событие, его ID хешируется $k$ раз. Если все $k$ бит уже установлены в 1, событие помечается как «вероятный дубликат» и отбрасывается.
- **Окно сброса:** Чтобы фильтр не заполнился полностью, он сбрасывается периодически (например, каждые 60 секунд). Это создаёт «скользящее окно» дедупликации.
- **Цена:** Постоянный объём памяти, сложность проверки $O(1)$, низкий процент ложных срабатываний (false positive).

### TTL (Time-To-Live)
В качестве финальной меры безопасности каждое сообщение `NetMessage` включает 1-байтовое поле `ttl`:
- **Декремент:** Каждый хост уменьшает `ttl` на 1.
- **Сброс:** Если `ttl` достигает 0, пакет уничтожается.
- **Цель:** Предотвращение бесконечных циклов при сходимости LSDB или в случае ошибок маршрутизации.

## 5. Изменения в Wire-протоколе

Для поддержки этих механизмов `NetMessage` расширяется:
- `source_id`: UUID оригинального отправителя события (должен быть UUID v4/v7, не читаемая строка).
- `event_id`: Уникальный UUID события (используется фильтром Блума).
- `ttl`: Счетчик времени жизни.
- `message_type`: `HELLO` (обновление топологии) или `EVENT` (данные).

**Важно:** Поля `source_id` и `event_id` **должны** быть UUID (v4 random или v7 time-ordered), а не читаемыми строками вроде `"host-a"` или `"console"`. Это требуется для:
1. **Глобальной уникальности** — никакой координации для назначения ID; каждый хост генерирует свой UUID при первом запуске.
2. **Дедупликации** — фильтр Блума опирается на равномерное распределение UUID для корректного процента ложных срабатываний.
3. **Отладки** — UUID непрозрачны, что предотвращает случайную связь с именами хостов/ролями.

Если текущий код использует строковые идентификаторы хостов (например, `"host-a"`, `"console"`), они должны быть заменены на UUID при реализации.

## 6. Сводка производительности

| Компонент | Память | Накладные расходы | Сложность |
|----------|--------|-------------------|------------|
| **Обнаружение** | $O(V + E)$ | Низкие (периодически) | $O(V+E)$ |
| **Маршрутизация** | $O(V)$ | Нулевые (поиск в таблице) | $O(1)$ |
| **Дедупликация** | Фикс. (4 КБ) | Нулевые | $O(k)$ |
| **TTL** | 1 байт | Нулевые | $O(1)$ |

*(V = количество хостов, E = количество связей)*

## 7. Рекомендуемые Rust-библиотеки

В этом разделе представлен анализ существующих Rust-крайтов, которые могут помочь в реализации описанных механизмов. Анализ основан на состоянии экосистемы Rust на 2024-2025 год.

### 7.1 Bloom Filter (Дедупликация)

| Крайт | Описание | Подходит? |
|-------|----------|-----------|
| **`fastbloom`** | SIMD-оптимизированный bloom filter (AVX2/NEON), `no_std`, фиксированный размер `[u64; N]`, XXH3 или SipHash | ✅ **Оптимальный** — продакшен-тестированный, SIMD-ускоренный, API `check_and_add()` |
| **`bloom`** | Классический bloom filter, фиксированный размер, `no_std` | ⚠️ Работает, но скалярный (без SIMD) |
| **`growable-bloom`** | Растущий bloom filter (несколько слоёв) | ❌ Нет — нам не нужен рост, только фиксированный + сброс |
| **`twox-hash`** + самописный | Быстрый 64-битный хеш XXH3 для k хеш-функций | ⚠️ Жизнеспособен, но `fastbloom` — тот же подход, продакшен-тестированный |

**Рекомендация:** `fastbloom` — SIMD-оптимизированный (AVX2/NEON), совместимый с `no_std`, фиксированный массив `[u64; N]` (точно наш случай 512 байт), с API `check_and_add(item) -> bool`, соответствующим семантике дедупликации. Используйте feature flag `xxh3` для не-криптографического хеширования (оптимально для дедупа).

Пример использования:
```rust
use fastbloom::FastBloom;

// 512 байт = 4096 бит, k=3 хеш-функции, хешер XXH3
let mut filter = FastBloom::with_num_bits_and_hasher(4096, 3, xxh3_64);

// Возвращает true, если элемент вероятно уже видели (дубликат)
if filter.check_and_add(event_id.as_bytes()) {
    // отбросить дубликат
}

// Оконный сброс (каждые 60 секунд)
filter.clear();
```

**Cargo.toml:**
```toml
[dependencies]
fastbloom = { version = "0.10", features = ["xxh3"] }
```

### 7.2 Graph + Shortest Path (Маршрутизация)

| Крайт | Описание | Подходит? |
|-------|----------|-----------|
| **`petgraph`** | Стандарт де-факто: Graph, DiGraph, BFS, Dijkstra, A* | ✅ Да — `petgraph::algo::dijkstra` возвращает карту расстояний, легко извлечь next-hop |
| **`pathfinding`** | Dijkstra, A*, BFS, DFS — более специализированный | ✅ Да — чуть более высокоуровневый |
| **`graph`** | Альтернатива petgraph | ⚠️ Менее популярен |

**Рекомендация:** `petgraph` — самый зрелый, хорошо документированный, `no_std` через `alloc`. Для andychoir (малые графы, <100 узлов) производительность не критична, но удобство API важно.

Пример использования:
```rust
use petgraph::graph::{Graph, NodeIndex, UnGraph};
use petgraph::algo::dijkstra;

let mut g = UnGraph::<&str, u32>::new_undirected();
let a = g.add_node("host-a");
let b = g.add_node("host-b");
let c = g.add_node("host-c");
g.add_edge(a, b, 1);
g.add_edge(b, c, 1);

// Dijkstra от цели для нахождения кратчайших путей
let dists = dijkstra(&g, c, None, |_| 1);
// next-hop = сосед с dist == 1 на кратчайшем пути к цели
```

### 7.3 Discovery / Gossip Protocol

| Крайт | Описание | Подходит? |
|-------|----------|-----------|
| **`libp2p`** | Полный стек: Kademlia DHT, mDNS, gossipsub, identify, ping | ⚠️ Тяжёлый, но имеет всё — можно использовать только `libp2p::kademlia` или `gossipsub` |
| **`memberlist`** | HashiCorp memberlist — SWIM gossip protocol | ❌ Нет официального Rust-порта (неофициальные есть, но сырые) |
| **`raft`** (например `raft-rs`, `openraft`) | Консенсус, не discovery | ❌ Нет — другая задача |
| **Самописный** | HELLO-пакеты поверх существующего WS-моста | ✅ Оптимально для andychoir |

**Рекомендация:** Для andychoir **самописная реализация** поверх существующего `net.rs` (WebSocket-мост). Причины:
- Уже есть `NetMessage` и `forward()` — достаточно добавить типы `HELLO`/`BYE`
- Малый масштаб (2-20 хостов) — полноценный gossip overkill
- `libp2p` тянет async, tokio, криптографию — избыточно для доверенной сети AI-хостов

Если всё же хочется готовое — `libp2p::swarm` + `libp2p::ping` + `libp2p::identify` дадут discovery из коробки, но ценой сложности и зависимостей.

## 8. Конфигурация и примеры

### 8.1 Что настраивает пользователь

Пользователь настраивает **только прямые линки** (`remotes`) — никогда всю
топологию. Каждый хост обнаруживает остальную mesh автоматически через flooding
HELLO и строит свою LSDB + FIB.

`NetConfig` (в `src/config/config.rs`):

```yaml
net:
  node_id: "00000000-0000-0000-0000-0000000000a1"  # UUID v4/v7 (генерируется, если невалиден)
  listen_port: 8090        # 0 = не слушать (хост-клиент за NAT)
  token: []                # токены, принимаемые на ВХОДЯЩИХ соединениях
  remotes:                 # персистентные ИСХОДЯЩИЕ WS-соединения (только прямые линки)
    - url: "ws://127.0.0.1:8091/net"
      token: "secret-b"
      targets: []          # опциональный pinned-роутинг (FIB имеет приоритет)
```

- `remotes` — список **прямых соседей**, к которым вы подключаетесь. Вы НЕ
  перечисляете здесь все хосты mesh — только те, с кем есть прямая связь.
- `targets` у remote — **опционален**. Если пуст, маршрутизация чисто по FIB
  (кратчайший путь). Если задан — явный pinned-роутинг как fallback.
- `listen_port: 0` означает «не принимаю входящие» (например, хост за NAT/роутером).
  Он всё равно подключается исходяще, а ответы приходят по тому же WebSocket
  (двунаправленный).

### 8.2 Формат target события

Чтобы обратиться к инструменту/агенту на **удалённом** хосте, target использует
префикс `host:`:

```
host:<node_id>:<tool>
```

Примеры:
- `host:00000000-0000-0000-0000-0000000000c3:tool:calculator` → запустить `tool:calculator`
  на хосте `…c3`, маршрутизация по FIB (возможно через промежуточные хопы).
- `tool:calculator` (без префикса `host:`) → локальный плагин, **не пересылается**.
- `agent:demo`, `mcp:…`, `session:…` → локальные (не пересылаются).

Когда мост получает событие с target, начинающимся на `host:`, он:
1. извлекает `<node_id>`,
2. ищет `next_hop` в FIB,
3. отправляет событие в канал next-hop (исходящий/входящий).

Поле `target` **сохраняется неизменным** вдоль пути — промежуточные хопы
перемаршрутизируют его так же (store-and-forward по next-hop).

### 8.3 Пример mesh из трёх хостов (A → B → C)

Топология: A и C оба подключаются напрямую к B; B — ретранзит. A не подключается к C.

**Хост A** (`listen_port: 0`, подключается к B):
```yaml
net:
  node_id: "00000000-0000-0000-0000-0000000000a1"
  listen_port: 0
  remotes:
    - url: "ws://127.0.0.1:8091/net"
      token: "secret-b"
```

**Хост B** (ретранзит, слушает 8091, никуда не подключается):
```yaml
net:
  node_id: "00000000-0000-0000-0000-0000000000b2"
  listen_port: 8091
  token: ["secret-b", "secret-c"]
  remotes: []
```

**Хост C** (`listen_port: 0`, подключается к B):
```yaml
net:
  node_id: "00000000-0000-0000-0000-0000000000c3"
  listen_port: 0
  remotes:
    - url: "ws://127.0.0.1:8091/net"
      token: "secret-c"
```

Поток при эмиссии A события `host:…c3:tool:calculator`:
1. HELLO от A (периодический) говорит B «я вижу A». HELLO от C говорит B «я вижу C».
   B флудит оба HELLO → A узнаёт «B видит C», C узнаёт «B видит A».
2. FIB A: `C → next_hop B`.
3. A пересылает событие B (в его канал `outbound[B]`).
4. B получает, перемаршрутизирует по FIB (`C → next_hop C` — прямой сосед),
   пересылает C.
5. C выполняет `tool:calculator` локально.

Никаких ручных `targets`, никакого центрального сервера — чистая link-state mesh.

### 8.4 Обработка сбоев

- **Тихий сбой:** если сосед не шлёт HELLO `LSDB_TIMEOUT_SECS` (30с), он удаляется
  из LSDB и FIB пересчитывается. Маршруты через него исчезают; альтернативные
  пути (если есть) вступают в силу.
- **Корректный выход:** при `drop()` моста всем соседям рассылается `BYE`,
  чтобы они сразу удалили узел.
- **Защита от петель:** каждый хоп декрементирует `ttl` (стартует с 16); при 0
  событие отбрасывается. Маршрутизация по кратчайшему пути на статическом
  снимке LSDB не создаёт петель; TTL — страховка при сходимости.

### 8.5 Retry, таймауты и защищённый от циклов discovery

**Повторное подключение (настраивается).** Каждый элемент `remotes` (и глобальный
`NetConfig`) принимает параметры retry:

```yaml
net:
  connect_retry_interval_secs: 10   # пауза между попытками (default 10)
  connect_timeout_secs: 300        # окно отказа (default 300 = 5 мин); 0 = вечно
  remotes:
    - url: "ws://127.0.0.1:8091/net"
      token: "secret-b"
      retry_interval_secs: 0        # 0 → из NetConfig (10)
      connect_timeout_secs: 0       # 0 → из NetConfig (300)
```

Это позволяет кольцу из 3 хостов собраться даже при неодновременном старте:
исходящая задача повторяет попытки (по умолчанию каждые 10с, до 5 мин), пока
пир не станет доступен. `0` для `connect_timeout_secs` означает «повторять вечно»
(полезно для долгоживущих mesh-линков в ненадёжных сетях).

**Защищённый от циклов discovery (mesh-циклы).** Mesh поддерживает топологические
циклы (A→B→C→A). Две механики держат это в безопасности:

1. **Соседи анонсируются по `node_id`, а не по URL.** `Hello.neighbors` несёт
   `node_id` прямых линков (из `node_url` / `incoming_senders`), поэтому граф LSDB
   строится согласованно во всей mesh — включая циклы.
2. **Монотонный `seq` в `Hello` (anti-loop flooding).** Каждый хост штампует
   свой `Hello` возрастающим `seq`. Узел игнорирует любой `Hello`, чей `seq ≤`
   последнему виденному `seq` от этого источника — поэтому `Hello`, вернувшийся
   по кольцу, отбрасывается вместо бесконечного рефлуда.

В сочетании с FIB по Дейкстре (кратчайший путь) и декрементом `ttl` на хопе,
события маршрутизируются корректно через циклы без бесконечного flooding и петель.

### 8.6 Безопасность транспорта: mTLS (шифрование + взаимная аутентификация между хостами)

По умолчанию mesh работает поверх **простого `ws://`** (tokio-tungstenite поверх TCP).
Обнаружение, маршрутизация и dedup не зашифрованы и не аутентифицированы на транспортном
уровне — единственная защита — токен `Auth` (B1, см. `docs/improvement-plan.md`). Чтобы
зашифровать межхозяйский трафик **и** взаимно аутентифицировать узлы, включите **mTLS**
(mutual TLS) с **внутренним приватным CA**, которым владеет развёртывание — без
публичных/сторонних CA.

> Реализовано в `src/host/net/tls.rs` и подключено в `server.rs` (входящие) и
> `outbound.rs` (исходящие). План: `docs/mtls-plan.md`. 129 юнит-тестов проходят, 0 warnings.

#### 8.6.1 Что даёт mTLS

- **Шифрование** — каждое межхозяйское соединение (и каждый хоп через ретранзит) — TLS;
  наблюдатель в сети больше не читает события/инструменты/сессии в процессе передачи.
- **Взаимная аутентификация** — оба конца обязаны представить сертификат, подписанный
  *нашим* внутренним CA. Хост с сертификатом не от нашего CA отвергается (на стороне
  сервера: клиентский сертификат обязателен; на стороне клиента: сертификат сервера
  должен цепляться к нашему CA).
- **Defense-in-depth** — токен `Auth` (B1) по-прежнему едет *поверх* зашифрованного
  канала, как второй фактор.

#### 8.6.2 Модель сертификатов

- Один **внутренний root CA** на развёртывание (self-signed). Его `ca.pem` распространяется
  на все хосты (внешним образом, напр. через вашу систему управления конфигурациями).
- У каждого хоста — **сертификат ноды**, выпущенный (подписанный) этим CA. SAN (DNS)
  сертификата **должен равняться `node_id` хоста** (конвенция `tls.rs`: SAN = `node_id`
  + loopback IP). `node_id` в hostname URL и SAN сертификата — одно и то же значение по
  конвенции (`NetRemote::url_host()` возвращает node_id).
- **Авто-генерация при первом старте:** если `ca.pem`/`node.pem`/`node.key` отсутствуют,
  `ensure_certificates()` генерирует внутренний CA + сертификат ноды автоматически (через
  `rcgen`) и пишет их в `mtls.dir`. Идемпотентно — если файлы есть и загружаются, ничего не
  перегенерируется. Удобно для одиночной dev/test-сборки; для продакшна развозите реальный
  CA и персональные сертификаты нод (задайте явные пути `ca_cert`/`cert`/`key`, оставьте
  `dir` пустым).

#### 8.6.3 Конфигурация (`MtlsConfig`)

`MtlsConfig` живёт под `net.mtls` (глобально) и под каждым `net.remotes[].mtls`
(переопределение на линк). Он `#[serde(default)]` — **выключен по умолчанию** (простой `ws://`).

```yaml
net:
  mtls:
    enabled: true
    dir: "./certs"            # где лежат/генерируются ca.pem/node.pem/node.key
    ca_cert: ""               # опциональный явный путь; "" → "<dir>/ca.pem"
    cert: ""                  # опциональный явный путь; "" → "<dir>/node.pem"
    key: ""                   # опциональный явный путь; "" → "<dir>/node.key"
    require_node_id_in_san: true   # строго: SAN сертификата партнёра == его node_id
```

- `enabled: false` (по умолчанию) → простой `ws://` (обратная совместимость). Токены применяются.
- `enabled: true` → хост слушает **`wss://`** и дозванивается до remote по **`wss://`**.
  URL в `remotes[].url` должны использовать схему `wss://`.
- `require_node_id_in_san`:
  - `false` → принимается «любой сертификат от нашего CA» (базовый mTLS). Узлы взаимно
    аутентифицированы относительно CA, но скомпрометированный сертификат другой ноды
    (выпущенный нашим CA) мог бы подключиться. Достаточно, когда CA жёстко контролируется.
  - `true` → строго: **клиент** дополнительно проверяет, что SAN сертификата сервера ==
    `node_id` сервера (берётся из hostname URL) через кастомный `ServerCertVerifier`.
    Это связывает TLS-идентичность с mesh-идентичностью. (См. ограничение ниже.)

> **Переопределение на линк:** remote может нести свой блок `mtls:`; если он есть и
> `enabled`, он переопределяет глобальный `net.mtls` только для этого линка. Поддерживаются
> смешанные mesh (часть линков plain, часть mTLS) — но plain-сервер отвергнет mTLS-клиента и
> наоборот; настраивайте оба конца согласованно.

#### 8.6.4 Ограничение (честно задокументировано)

Строгая привязка SAN↔node_id реализована на **стороне клиента** (дозванивающийся хост
проверяет SAN сертификата сервера против hostname URL). Строгая проверка SAN клиента на
**стороне сервера** **не** реализована, потому что сервер узнаёт `node_id` клиента только
после сообщений `Auth`/`Hello`, которые приходят *после* TLS-handshake. Реализация проверки
в verifier потребовала бы передачи node_id до handshake (изменение wire-протокола). Базовая
взаимная проверка CA (клиентский сертификат обязателен + цепочка к нашему CA) реализована
полностью и закрывает главную угрозу (шифрование + взаимная аутентификация CA). Для
продакшна предпочтительно развозить персональные сертификаты нод и держать
`require_node_id_in_san: true` на дозванивающейся стороне.

#### 8.6.5 Пример mTLS mesh (A → B → C, зашифровано)

Все три хоста используют один внутренний `ca.pem`. У каждого хоста свой `node.pem`/`node.key`
(SAN = его `node_id`). Добавляется только `net.mtls` по сравнению с §8.3; маршрутизация/FIB
не меняется.

**Хост A** (`listen_port: 0`, дозванивается до B по `wss://`):
```yaml
net:
  node_id: "00000000-0000-0000-0000-0000000000a1"
  listen_port: 0
  mtls:
    enabled: true
    dir: "./certs"
    require_node_id_in_san: true
  remotes:
    - url: "wss://127.0.0.1:8091/net"
      token: "secret-b"
```

**Хост B** (ретранзит, слушает `wss://8091`):
```yaml
net:
  node_id: "00000000-0000-0000-0000-0000000000b2"
  listen_port: 8091
  token: ["secret-b", "secret-c"]
  mtls:
    enabled: true
    dir: "./certs"
  remotes: []
```

**Хост C** (`listen_port: 0`, дозванивается до B по `wss://`):
```yaml
net:
  node_id: "00000000-0000-0000-0000-0000000000c3"
  listen_port: 0
  mtls:
    enabled: true
    dir: "./certs"
    require_node_id_in_san: true
  remotes:
    - url: "wss://127.0.0.1:8091/net"
      token: "secret-c"
```

Когда A эмитит `host:…c3:tool:calculator`, событие пересылается A→B→C **внутри TLS**;
каждый хоп валидирует сертификат партнёра относительно внутреннего CA и (при
`require_node_id_in_san`) относительно `node_id` партнёра. Пассивный наблюдатель в сети
видит только шифртекст.
