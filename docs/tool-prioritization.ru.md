# Приоритезация инструментов (Origin-Aware)

Данный документ описывает дизайн и план реализации механизма приоритезации инструментов на основе узла-инициатора запроса.

## 1. Цель
Когда агент принимает решение использовать инструмент, система должна в первую очередь пытаться запустить его на хосте, который инициировал запрос («хост-источник»). Это позволяет сократить сетевые задержки, обеспечить локальность данных (доступ к локальным файлам/состоянию клиента) и снизить общую нагрузку на сеть.

## 2. Архитектура
Логика приоритезации реализуется на уровне **Хоста/Оркестратора**. Сам LLM-агент остается «слепым» к топологии сети — он просто запрашивает инструмент по имени (например, `tool:calculator`), а инфраструктура хоста самостоятельно разрешает этот запрос в конкретный сетевой таргет.

### Иерархия выбора инструментов (3 уровня приоритета)

Когда Оркестратор получает запрос `tool:T` для сессии $S$, он следует следующему порядку поиска:

#### Уровень 1: Хост-источник (Высший приоритет)
*   **Проверка:** Обладает ли хост, инициировавший сессию $S$, инструментом `T`?
*   **Источник данных:** `NetInner.session_origin` $\to$ `NetInner.origin_tools[source_id]`.
*   **Результат:** Если найден $\to$ таргет = `host:<Source_ID>:tool:T`.

#### Уровень 2: Локальный хост (Средний приоритет)
*   **Проверка:** Обладает ли текущий хост (на котором запущен агент) инструментом `T`?
*   **Источник данных:** `crate::plugin::engine::local_tools()`.
*   **Результат:** Если найден $\to$ таргет = `tool:T` (локальное выполнение).

#### Уровень 3: Общая сеть (Низший приоритет)
*   **Проверка:** Обладает ли любой другой хост в mesh-сети инструментом `T`?
*   **Источник данных:** `NetInner.origin_tools` (все остальные узлы).
*   **Результат:** Если найден $\to$ таргет = `host:<Remote_ID>:tool:T`.
*   **Выбор:** Если инструмент доступен на нескольких узлах, выбирается тот, до которого кратчайший путь согласно FIB.

---

## 3. Поток логики (Logic Flow)

1. **Запрос:** Агент возвращает команду `tool:T`.
2. **Определение источника:** Оркестратор извлекает `source_id` из `session_origin` для текущей сессии.
3. **Поиск по уровням:**
    - Поиск в `origin_tools[source_id]` $\to$ найдено? Возврат `host:source_id:tool:T`.
    - Поиск в `local_tools()` $\to$ найдено? Возврат `tool:T`.
    - Поиск по всем `origin_tools` $\to$ найдено? Возврат `host:remote_id:tool:T`.
    - Не найдено $\to$ Ошибка «Инструмент не доступен в сети».
4. **Маршрутизация:** Разрешенный таргет передается в `forward()`, который осуществляет доставку через FIB.

**Особый случай:** Если агент явно указал конкретный таргет (например, `host:C:tool:calculator`), Оркестратор **не должен** переопределять его, позволяя агенту вызвать конкретный «профессиональный» инструмент, даже если есть локальный аналог.

## 4. План реализации

### Фаза 1: Расширение API
*   Реализовать вспомогательную функцию `resolve_tool_target(session_id, tool_name)` в Оркестраторе.
*   Обеспечить доступ к `NetInner` (для `session_origin` и `origin_tools`) и локальному реестру плагинов.

### Фаза 2: Интеграция
*   Внедрить `resolve_tool_target` в цикл обработки событий: вместо прямого проброса `tool:T` Оркестратор сначала разрешает оптимальный таргет.
*   Добавить отладочное логирование: `[Оркестратор] Инструмент 'T' разрешен для хоста X (Приоритет: Уровень N)`.

### Фаза 3: Верификация
*   **Unit-тесты:** Мокирование `NetInner` с различными распределениями инструментов и проверка итоговых таргетов.
*   **Интеграционный тест (Кольцевая топология):**
    *   Настройка: Нода A (Фронт), Нода B (Агент), Нода C (Инструмент).
    *   Сценарий 1: Инструмент есть на A $\to$ Проверка пути B $\to$ A.
    *   Сценарий 2: Инструмент только на C $\to$ Проверка пути B $\to$ C.
    *   Сценарий 3: Инструмент только на B $\to$ Проверка локального выполнения.
